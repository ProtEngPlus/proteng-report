# ProtEngPlus — ข้อเท็จจริงของ ML pipeline

บันทึกนี้ลงรายละเอียดของแต่ละขั้นตอนใน pipeline ว่าใช้วิธีไหน ต้องการ input อะไร คืนอะไร
และใช้เวลาเท่าไร ตรวจกับโค้ดบน branch `dev` ของ `proteng-kubeflow` และ `proteng-conductor`
เมื่อ 2026-11-10

ML service ทุกตัวอยู่ใน repo `proteng-kubeflow` โดยหนึ่ง service คือหนึ่งโฟลเดอร์ใน `projects/`
ชื่อ repo เป็นชื่อตามประวัติ ปัจจุบันไม่มีส่วนใดใช้ Kubeflow แล้ว

## 1. รูปแบบร่วมของทุก service

ทุก service เป็น RabbitMQ consumer ที่ไม่มี HTTP port รับเข้า การทำงานหนึ่งรอบเป็นแบบนี้
`proteng-conductor` publish message ของ stage ปัจจุบันเข้า topic exchange ชื่อ `logs_topic`
ด้วย routing key รูปแบบ `<stage>.<tool>` เช่น `query.mmseqs2` หรือ `mutation.mutation`
consumer ของ stage นั้นรับ message จาก queue ของตัวเอง รันงานใน thread แยก อ่านและเขียน artifact
ใน Google Cloud Storage แล้ว publish ผลกลับเข้า queue ชื่อ `job_status_event` ซึ่ง conductor
เป็นผู้อ่านและตัดสินว่าจะเดิน stage ถัดไปหรือจบงาน

ผลของแต่ละ stage เดินทางผ่าน RabbitMQ และ GCS เท่านั้น conductor ไม่แตะ GCS เลย
มีเพียง ML consumer และปุ่มดาวน์โหลดบนหน้าเว็บที่อ่านหรือเขียน artifact

การเพิ่มเครื่องมือใหม่ให้ขั้นตอนใดก็ตามจึงทำได้โดยเพิ่ม consumer ที่ผูกกับ routing key ใหม่
ไม่ต้องแก้ state machine หลักของ conductor ซึ่งเป็นคุณสมบัติที่ออกแบบงาน evaluation plugin
ของปีนี้ไว้บนพื้นนี้

## 2. ขั้นตอน query (stage 0)

ขั้นตอนนี้หา homolog คือโปรตีนที่มีลำดับใกล้เคียงกับ sequence ตั้งต้น เพื่อใช้เป็นข้อมูลให้
ขั้นตอนถัดไปปรับโมเดลภาษาโปรตีน ผู้ใช้เลือกได้สองเครื่องมือ

**blast** เรียก NCBI BLAST ผ่าน Biopython ด้วย `NCBIWWW.qblast` ข้อดีคือผลตรงกับเว็บของ NCBI
และฐานข้อมูลใหญ่ ข้อเสียคือเวลาไม่คงที่และควบคุมจากฝั่งเราไม่ได้เลย ทีมวัดเวลาจริง 15 รอบ
เมื่อ 2026-08-31 ด้วย query และพารามิเตอร์ชุดเดียวกันทุกครั้ง ได้ผลตามตารางนี้

| สถิติ | นาที |
| --- | --- |
| เร็วที่สุด | 4.3 |
| median | 12.3 |
| mean | 19.4 |
| ช้าที่สุด | 40.3 |

การกระจายเบ้ขวา มี 6 รอบจาก 15 รอบที่เกินครึ่งชั่วโมง และช่วงเวลาของวันมีผลชัดเจน สรุปที่ใช้
อ้างในรายงานได้คือ BLAST ผ่าน NCBI ใช้ทำ SLA หรือการสาธิตที่ต้องการเวลาแน่นอนไม่ได้

**mmseqs2** รันโปรแกรม MMseqs2 บนเครื่องของทีมเองกับฐาน Swiss-Prot ซึ่งเก็บเป็นไฟล์ FASTA
ขนาดประมาณ 286 MB ใน repo ด้วย Git LFS เวลาที่ใช้อยู่ในระดับไม่กี่นาทีและคาดเดาได้
ทีมจึงแนะนำตัวนี้สำหรับการสาธิต

ผลลัพธ์ของขั้นตอนนี้ถูกกรองด้วยเงื่อนไขความยาวและ query cover ก่อนส่งต่อ โดยงานในเดือนตุลาคม
เปลี่ยนไปอ่านผล BLAST ด้วย NCBIXML ให้ได้หนึ่งแถวต่อหนึ่ง hit คิด query cover เทียบกับความยาว
ของ query และส่ง sequence ของ hit แบบเต็มความยาวแทนเฉพาะส่วนที่ align กัน

## 3. ขั้นตอน evotune (stage 1)

ขั้นตอนนี้ปรับโมเดลภาษาโปรตีนให้เข้ากับตระกูลโปรตีนที่สนใจ โดยใช้ homolog จาก stage 0
เป็นข้อมูล ผลที่ได้คือโมเดลที่แปลง sequence เป็นเวกเตอร์ตัวเลข ซึ่งเรียกว่า representation

ตัวเลือกแรกคือ **Unirep** ซึ่งใช้ `jax-unirep` 2.2.0 เป็น mLSTM ที่ให้เวกเตอร์ขนาด 64 มิติ
ตามที่ปรากฏใน `projects/mutation/src/service/directed_evo.py` ตัวเลือกนี้เป็นของเดิมที่รุ่นก่อนทำไว้

ตัวเลือกที่สองคือ **ESM** ซึ่งเป็นโมเดลภาษาโปรตีนจาก Hugging Face โดยรุ่นที่ใช้คือ
`facebook/esm2_t30_150M_UR50D` ตามค่าใน `pkg/common/esm.py` ใช้ `torch` กับ `transformers`
และควรมี GPU
เดิมเป็น proof of concept ที่ยังไม่ต่อเข้า pipeline จริง งานในสัปดาห์ปลายเดือนตุลาคม 2026
ทำให้ใช้งานได้จริง คือ job ที่เลือก ESM ถูกส่งไปที่ consumer ที่ถูกตัว รับผลจาก MMseqs2 ได้
และเก็บโมเดลที่ fine-tune แล้วไว้ใช้สร้าง embedding ทั้งในขั้น fittop และขั้น mutation
หลักฐานที่เห็นได้ชัดคือ `requirements.txt` ของ fittop และ mutation มี `torch` กับ
`transformers` เพิ่มเข้ามาแล้ว ทั้งที่สองขั้นนี้เดิมใช้เพียง jax ส่วนนี้อยู่บน `dev`
และยังไม่ได้ปล่อยขึ้น production

## 4. ขั้นตอน fittop (stage 2)

ขั้นตอนนี้ฝึกโมเดลทำนาย assay score จากผลแล็บที่ผู้ใช้อัปโหลด โดยใช้ representation จาก stage 1
เป็น feature ปัจจุบันมีอัลกอริทึมเดียวคือ **RidgeCV** ซึ่งเป็น ridge regression ที่เลือกค่า
regularization ด้วย cross-validation

ข้อจำกัดที่ต้องรู้คือ RidgeCV แก้สมการแบบปิด จึงไม่มีการฝึกต่อจากโมเดลเดิม ทุกครั้งคือคำนวณใหม่
จากผลแล็บทั้งกอง ข้อนี้เป็นที่มาของ feature ที่วางแผนไว้ว่าจะให้ฝึกใหม่เมื่อมีผลแล็บชุดใหม่
โดยรวมผลเก่ากับผลใหม่เข้าด้วยกันแล้วข้ามสองขั้นตอนแรกที่ใช้เวลานาน

## 5. ขั้นตอน mutation (stage 3)

ขั้นตอนนี้เสนอ mutant พร้อมค่า assay score ที่ทำนายได้ วิธีที่ใช้คือ directed evolution
แบบ Metropolis-Hastings ซึ่งเป็น Monte Carlo optimization ตามที่เห็นใน `directed_evo.py`

การทำงานหนึ่ง trajectory เป็นแบบนี้ เริ่มจาก wild-type แล้วสุ่ม mutant ตั้งต้นภายในขอบเขต
ที่กำหนด จากนั้นวนตามจำนวน iteration โดยแต่ละก้าวจะเสนอ mutation ใหม่ คำนวณ predicted score
แล้วรับก้าวนั้นด้วยความน่าจะเป็นที่ขึ้นกับผลต่างของ score และค่า temperature คือถ้าคะแนนดีขึ้น
จะรับแน่นอน ถ้าคะแนนแย่ลงจะยังมีโอกาสรับตามสูตร exponential เมื่อครบ iteration จะคืน sequence
ที่ดีที่สุดของ trajectory นั้นพร้อมคะแนน ระบบรันหลาย trajectory แล้วรวมผล

พารามิเตอร์ที่ผู้ใช้คุมได้รวมถึงจำนวน trajectory, จำนวน iteration, temperature, ช่วงตำแหน่ง
ที่อนุญาตให้ mutate และจำนวนตำแหน่งที่เปลี่ยนได้อย่างต่ำและอย่างสูง สองอย่างหลังเป็นงานที่เพิ่ม
ในเดือนตุลาคม 2026 แทนพารามิเตอร์เดิมที่เป็นเลขตัวเดียวและความหมายจริงในโค้ดไม่ตรงกับชื่อ
นอกจากนี้ระบบยังจำกัดให้ mutate เป็นกรดอะมิโนมาตรฐาน 20 ตัวเท่านั้น

เวลาที่ใช้ของขั้นตอนนี้วัดบน production เมื่อ 2026-09-29 ได้ประมาณ 15 วินาทีที่ค่าเริ่มต้น
คือ 5 trajectory คูณ 25 iteration และรันบน CPU

ข้อจำกัดที่ยังอยู่คือ service คืนเฉพาะ sequence ที่ดีที่สุดของแต่ละ trajectory ถ้ารัน
5 trajectory จะได้ 5 เส้น การเก็บ mutant ทุก iteration แล้วคัดเฉพาะกลุ่มที่ดีที่สุด
เป็น feature ที่วางแผนไว้แต่ยังไม่ได้ทำ

## 6. ขั้นตอน evaluation

นี่คือส่วนที่เป็นงานหลักของปีนี้ ความต้องการตั้งต้นคือ stakeholder อยากประเมิน mutant
ได้หลายแบบหลังจาก mutation เสร็จ เช่นดูความเสถียรของการพับโปรตีนและดูประสิทธิภาพการเร่งปฏิกิริยา
แต่ pipeline เดิมเป็นสี่ขั้นตายตัวและจบที่ mutation ไม่มีที่ให้ต่อ

สิ่งที่ทำไปแล้วคือกลไกที่ทำให้ขั้นตอนนี้ต่อท้ายได้ ได้แก่ การเริ่ม evaluation ต่อจาก mutation
เมื่อผู้ใช้เลือก plugin ไว้, การรัน plugin เรียงทีละตัวจนครบ, การ snapshot ว่า mutant ชุดใด
จะถูกประเมินเพื่อให้ผลที่วิ่งกลับมาเพิ่ม mutant อื่นเข้ามาไม่ได้, การตั้ง run เป็น fail
เมื่อไม่ได้ผลกลับมาในเวลาที่กำหนด, การเก็บผลของแต่ละ plugin ต่อ mutant หนึ่งเส้นในรูป map
จึงรองรับ plugin ที่คืนค่าต่างรูปแบบกันได้, การถือว่า job เสร็จสมบูรณ์เมื่อ run จบ
และการสั่งรันรอบใหม่สำหรับ job ที่เสร็จแล้ว

ฝั่งหน้าเว็บมีการเลือก plugin ตอนสร้าง job, การสั่งรันรอบใหม่จากหน้า JobDetail, การแสดง run
กับผลลัพธ์ และการแสดงขั้นตอนนี้บน dashboard

สิ่งที่ยังไม่มีคือ plugin จริง ปัจจุบันมีเพียง `evaluation_mock` ซึ่งเป็น consumer ที่ใช้ทดสอบ
เส้นทางของ message ส่วน plugin ที่วางแผนไว้คือ stability ที่ทำนายค่า ΔΔG เทียบกับ wild-type
และ kcat ที่ใช้โมเดล DLKcat ซึ่งต้องรับ substrate เป็น SMILES เพิ่มเข้ามาเป็น input ใหม่
ทั้งสองยังไม่ได้ลงมือ

## 7. artifact และลำดับการส่งต่อ

input ของแต่ละ stage คือ output ของ stage ก่อนหน้า ไม่มีโมเดลที่ฝึกมาจากข้างนอก ลำดับเป็นแบบนี้

```text
query (blast หรือ mmseqs2) -> similar_protein -> evotune -> unirep -> fittop -> ridgecv -> mutation -> mutation
```

ชื่อหลังลูกศรคือชื่อ bucket ใน GCS ที่เก็บผลของ stage นั้น ตอนรันบนเครื่อง local ทีมใช้
GCS emulator ที่เตรียม bucket ทั้งสี่ไว้ให้ จึงรัน pipeline เต็มได้โดยไม่ต้องมี credential
ของ GCP จริง

## 8. ข้อจำกัดของสภาพแวดล้อมที่รัน ML

ML consumer ทั้งหมดรันบน GPU VM เครื่องหนึ่งที่ทีมไม่ได้เป็นผู้ดูแล cloud project จึงไม่มี sudo
ไม่มี Docker และเปลี่ยน firewall ไม่ได้ ทุกอย่างบนเครื่องเป็น Python virtual environment
ที่ประกอบขึ้นเอง เครื่องใช้ Python 3.10.12 ซึ่งหมดระยะ support ไปแล้วตั้งแต่ 2026-10-01
และ jax ที่ติดตั้งไว้เป็นรุ่น CPU อย่างเดียว งาน ML ส่วนใหญ่จึงรันบน CPU แม้เครื่องจะมี GPU

ข้อจำกัดเรื่อง dependency ที่ต้องระวังคือ jax-unirep รุ่นใหม่เปลี่ยน API, aio_pika รุ่น 10
ต้องใช้ Python 3.11 ขึ้นไป และ jax-unirep ยังเรียก `pkg_resources` ที่ถูกถอดออกจาก setuptools
รุ่นใหม่ ทีมจึง pin เวอร์ชันของทุก package ตามที่รันอยู่บนเครื่องจริง และบังคับให้ venv
บนเครื่อง local ใช้ Python 3.10 เพื่อให้ได้ package ชุดเดียวกัน
